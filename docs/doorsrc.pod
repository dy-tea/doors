=head1 NAME

doorsrc - startup script for the doors Wayland compositor

=head1 SYNOPSIS

B<$XDG_CONFIG_HOME/doors/doorsrc>

B<$HOME/.config/doors/doorsrc>

B<doors -c> I<DIR>

=head1 DESCRIPTION

I<doorsrc> is a shell script that doors runs once, at startup, after the
compositor has initialised.

Because it is an ordinary shell script, it can run arbitrary commands and
start programs. It is executed by the shell, so quoting rules are those of
the shell: quote patterns that contain C<*>, C<[> or C<{>.

The file is looked up in the configuration directory, which defaults to
I<$XDG_CONFIG_HOME/doors/> (or I<$HOME/.config/doors/>). A different
directory can be passed to doors with the B<-c> option.

=head1 WHEN IT RUNS

I<doorsrc> runs exactly once, at startup. It is not re-run on demand:
re-running it would launch the applications it starts a second time. For
changes made while doors is running, use I<doorsctl> directly (C<config>,
C<rule>, C<hotkey>, ...).

Editing I<doorsrc> after startup is noticed: doors announces it through
C<doorsctl subscribe config> as a C<config_changed> event. Nothing in the
file is applied automatically in response; the announcement is only a
notification so that external tooling can react.

Defaults for settings are captured at startup, before I<doorsrc> runs, so
C<doorsctl config --list --changed> reports exactly what the config altered.

=head1 ENVIRONMENT

Doors keeps its own process environment, inherited by applications launched
later by doors (including hotkey commands). Update it from I<doorsrc> with

    doorsctl env set NAME value
    doorsctl env unset NAME

An C<export> in I<doorsrc> only changes the environment of that shell and of
commands launched directly by it; a child process cannot modify the
environment of the already-running doors parent. If a value is needed by
both, do both explicitly:

    export XCURSOR_SIZE=24
    doorsctl env set XCURSOR_SIZE "$XCURSOR_SIZE"

Environment variables that doors itself needs while initialising must still
be set before launching doors; IPC is only available after initialisation, so
they cannot be supplied through I<doorsrc>.

=head1 CONFIGURING SETTINGS

Settings are changed with C<doorsctl config NAME VALUE> and reset with
C<doorsctl config reset NAME...>. See L<doorsctl(1)> for the full list of
settings, types and accepted ranges.

Common examples:

    doorsctl config border_width 2
    doorsctl config window_gap 12
    doorsctl config borderless_monocle true
    doorsctl config gapless_monocle true
    doorsctl config enable_animations true

=head1 DESKTOPS AND OUTPUTS

Set up the desktops on an output:

    doorsctl output HDMI-A-1 -d I II III IV V VI VII VIII IX X

Outputs, modes, positions and other display properties are configured with
C<doorsctl output>; see L<doorsctl(1)>.

=head1 WINDOW RULES

Window rules control how specific applications are managed when they open.
They are added from I<doorsrc> with C<doorsctl rule -a>. At most 128 rules
may be defined at once. Rules are appended and the last matching rule wins.

    doorsctl rule -a dev.zed.Zed desktop=I follow=off
    doorsctl rule -a firefox desktop=II state=floating

See L<doorsctl(1)> for the full consequence and matching syntax.

=head1 PERMISSIONS

Permission policy for unsandboxed clients is set with C<doorsctl permission>.
Rules are appended and the last matching rule wins.

    doorsctl permission 'exe:*grim' capture=allow
    doorsctl permission 'exe:*' capture=ask

See L<doorsctl(1)>.

=head1 EXAMPLE

A minimal I<doorsrc>:

    #!/bin/sh

    doorsctl output HDMI-A-1 -d I II III IV V VI VII VIII IX X

    doorsctl config border_width 2
    doorsctl config window_gap 12
    doorsctl config borderless_monocle true
    doorsctl config gapless_monocle true
    doorsctl config enable_animations true
